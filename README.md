# Модус Сигнал

Работающий MVP системы обратной связи и предложений сотрудников ГК «Модус Трейд» для хакатона.

Сотрудник сообщает о проблеме или предлагает улучшение. Система регистрирует обращение, назначает ответственного и сроки. Автор видит ход рассмотрения и итог, руководитель — просрочки, повторяющиеся проблемы и результаты. Цель — уменьшить потери обращений и сделать ответственность за результат прозрачной.

## Запуск проекта

Требуется **Node.js 20 или новее**. Внешних npm-зависимостей нет: `npm install` и сборка не нужны. **API-ключи и токены для демонстрации не требуются.**

```sh
git clone https://github.com/arrmanelo/modus.trade.git modus-signal
cd modus-signal
```

Если проект получен архивом, откройте распакованную папку с `package.json` и `start.cmd`. Все команды выполняются из папки проекта.

**Windows:** откройте `start.cmd` двойным щелчком или выполните в PowerShell:

```powershell
.\start.cmd
```

**Linux / macOS:**

```sh
NODE_ENV=development HOST=127.0.0.1 DEMO_LOGIN=1 DEMO_TOOLS=1 BITRIX24_WEBHOOK_URL= npm start
```

Откройте **http://localhost:3000** и выберите демонстрационного пользователя. Остановка сервера — `Ctrl+C`.

Если в окружении установлен `NODE_ENV=production`, демо-вход отключён. Для локального показа задайте `NODE_ENV=development`. При занятом порте задайте другой `PORT` перед запуском, например `$env:PORT='3001'` в PowerShell.

## Роли и доступ

| Роль | Возможности |
| --- | --- |
| Сотрудник | Создаёт обращения с файлами, следит за своими обращениями, отвечает на уточнения, оценивает результат, читает инструкции и публичные идеи коллег. |
| Ответственный | Видит свою очередь и эскалации, рассматривает обращения, запрашивает уточнения, фиксирует решения и ведёт инструкции. Аналитика и «Эффект сервиса» недоступны. |
| Руководитель | Обрабатывает обращения в зоне ответственности, назначает исполнителей, контролирует сроки, использует аналитику, CSV и «Эффект сервиса». |
| Администратор | Настраивает категории, маршрутизацию, сроки и замещения; имеет доступ к общей аналитике и управлению системой. |

Права проверяются на сервере. Публичные обращения видны коллегам; непубличные — автору и участникам обработки по правилам доступа. Вложения и внутренние заметки имеют отдельные ограничения. Анонимная подача скрывает имя в интерфейсе, но не защищает личность автора от оператора сервера.

## Реализованные функции

- Проблемы, предложения и положительные отзывы: категории, приоритеты, описание и вложения.
- Автоматическое назначение ответственного, замещение отсутствующего сотрудника и резервный маршрут.
- Статусы, комментарии, запросы уточнений, история, итоговое решение и мотивированный отказ.
- Сроки первого ответа и решения, просрочки, пауза на уточнение и эскалации.
- Поиск и фильтры по подразделению, категории, статусу и срокам; карточки и таблица.
- Поиск похожих обращений на основе TF-IDF, объединение дублей и поддержка идей.
- Инструкции и ответы, подсказки перед подачей обращения, фиксация самостоятельного решения.
- Уведомления внутри приложения, оценка результата и доска реализованных улучшений.
- Главные страницы по ролям, аналитика, CSV, «Эффект сервиса» и демо-тур.
- Светлая тема при загрузке интерфейса.

## Тестовые данные

При первом запуске автоматически создаются **40 синтетических обращений**. A-001…A-020 основаны на датасете хакатона, A-021…A-040 добавлены для демонстрации. Имена, даты, история, оценки и дополнительные решения вымышлены. Даты добавлены для демонстрации сроков: в исходном датасете их нет.

Состояние сохраняется в `data/db.json`, локальный секрет — в `data/secret.key`. Папка `data/` не публикуется в Git. Для чистого демо без удаления текущих данных задайте новую папку через `DATA_DIR`, например `$env:DATA_DIR='data-demo'` перед запуском в PowerShell.

## Архитектура

```text
Браузер: HTML / CSS / JavaScript
                  ↓ HTTP API
Node.js: авторизация, права, бизнес-правила
                  ↓
JSON-хранилище и очередь интеграций
```

Стандартные средства Node.js и JavaScript позволяют запускать MVP без внешней СУБД и сборки интерфейса. JSON упрощает демонстрацию, но ограничивает масштабирование.

Основные сущности: пользователь, подразделение, категория, правило маршрутизации, обращение, вложение, событие истории, уведомление, инструкция и запись очереди интеграций.

| Папка | Назначение |
| --- | --- |
| `web/` | Интерфейс, стили, шрифты и демо-тур. |
| `core/` | Модель, права, маршрутизация, сроки, аналитика, инструкции и демо-данные. |
| `server/` | HTTP-сервер, сохранение данных и адаптер Битрикс24. |
| `tests/` | Приёмочные проверки, безопасность и инструкции. |
| `scripts/` | Проверка синтаксиса и ресурсов. |
| `docs/` | Дополнительные материалы для защиты. |

## Безопасность и режим с паролями

Реализованы серверные проверки прав, вход по паролю, scrypt с солью, сессии на 12 часов в HttpOnly-cookie с SameSite=Strict, завершение сессий при выходе и смене пароля. Есть ограничения попыток входа и частоты запросов, валидация, CSRF-защита и CSP.

Вложения проверяются по расширению и содержимому: до **5 файлов**, до **2 МБ каждый**, до **8 МБ суммарно**. Секреты, локальная база и журналы исключены через `.gitignore`.

Для режима с паролями задаются `NODE_ENV=production`, `APP_SECRET` от 32 символов, HTTPS и `COOKIE_SECURE=1`. Начальный пароль администратора — `ADMIN_PASSWORD`. Полный список параметров: [.env.example](.env.example). Передавайте параметры через окружение процесса: обычный `npm start` сам файл `.env` не загружает. `start.cmd` предназначен для локальной демонстрации.

## Ограничения MVP

- Один серверный процесс и JSON-хранилище. Нет транзакционной СУБД и автоматических резервных копий. При аварии возможна потеря последних изменений до сохранения. Несколько процессов с общей папкой данных не поддерживаются.
- Лимиты запросов хранятся в памяти и сбрасываются при перезапуске.
- Рабочие сроки учитывают выходные, но не праздничный календарь. Фоновые проверки выполняются при работающем сервере.
- Нет корпоративного SSO и антивирусной проверки вложений. Демо-вход выбором роли предназначен для локального показа.
- Данные и метрики демонстрационные. Эффект на реальных процессах компании ещё не измерялся.
- Клиентская обратная связь, NPS и другие опросы не входят в MVP.

## План развития и проверка ценности

1. **Пилот в подразделении:** согласовать категории, ответственных и сроки; проверить удобство подачи и обработки на рабочих сценариях с разрешёнными данными.
2. **Подготовка к эксплуатации:** PostgreSQL, резервные копии, общие лимиты через Redis, мониторинг, проверка безопасности, SSO и проверка вложений.
3. **Корпоративные интеграции:** испытать Битрикс24 на тестовом портале, согласовать обмен с 1С и организационную структуру.
4. **Расширение продукта:** клиентская обратная связь, опросы и NPS после проверки внутреннего процесса.

Полезность пилота оценивается по времени первого ответа, доле обращений с результатом, просрочкам, количеству реализованных улучшений и оценкам авторов. Базовые и целевые значения определяются вместе с компанией до пилота.
